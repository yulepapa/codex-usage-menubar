# Validation scope

Version 1.2.1 adds individual reset-credit cards. Model checks exercise expiry/ID ordering, deduplication, unknown/stale/future/failed inventory, count-only and contradictory counts, expired entries, implicit earliest versus explicit identity selection, changed expiry, removed selections and traversal of 100 cards with at most three visible. The native synthetic diagnostic also renders zero/one/three/tied/many/selected/hover/stale/mismatch/pending states. It uses the actual view's coordinate hit-testing and NSButton actions, checks fixed hover hit frames and crossing-event order, refresh remapping, immediate detail opening, normal/reduced-motion hover, Arrow/Enter/Space/Tab, and verifies card operations call none of the settings or refresh callbacks. Card selection has no account, store or consumption path; existing expiry policy and overall pending/error presentation remain unchanged. These remain synthetic native renders and programmatic events, not real mouse movement or screen capture.

Version 1.2.0 introduces the approved 660 × 414 AppKit popover. Pure display-model tests cover response-driven one/two/absent windows, missing reset times, Seoul date boundaries, saved on/off settings, disabled controls, fresh/stale/future/failed reset data, durable nothingToReset, pending priority, confirmed use, noCredit and time-only 1200-second display boundaries. The worker, engine, ledger and existing safety tests remain unchanged. The closed status-bar image configuration, default font and numeric-format functions are retained.

`CodexUsage.app/Contents/MacOS/CodexUsage --export-popover-fixtures /tmp/codex-popover-fixtures -AppleLanguages '(ko)'` is an explicit synthetic-only diagnostic; it initializes neither the live AppDelegate nor a store/account client/worker. It renders the same native view into nine 1320 × 828 PNGs, checks mock auto-use/reminder/refresh callbacks and failed-save restoration, 250 ms switch and 400 ms ticket animation, Reduce Motion, accessibility labels/values, keyboard focus/Tab, and three programmatic NSPopover open/update/Escape-close cycles. The diagnostic requires an ordinary logged-in macOS GUI session. Its first shell-sandbox run could not register NSApplication; a normally approved execution succeeded. An initial lifecycle check exposed missing test-harness AppKit event dispatch; explicit dispatch and anchor readiness resolved it. These are native-view renders and programmatic AppKit interactions, not screenshots or physical clicks. Live screen appearance, outside-click dismissal, VoiceOver speech, actual notification banners and real redemption remain unverified by this fixture path. No real setting or account was changed and no notification permission was requested by the diagnostic.

Version 1.1.5 adds an engine-to-menu regression for `nothingToReset`: the warning remains visible after worker ticks and restarts at 60, 120 and 179 seconds, without another consume call or key change. At 180 seconds the service can be retried; a confirmed success replaces the warning. The menu is also checked from inside the fresh-read callback against the saved `checking` state, before that read returns. Simulated timeout, interruption at that save and a restarted worker whose next read fails all preserve the known result without implying a successful current query. Missing, expired or changed credits, unknown/zero counts, future-dated attempts and elapsed retry windows do not revive an old no-op warning. Pending or uncertain results retain priority, and a newer terminal outcome supersedes an earlier no-op, including equal attempt timestamps. A second read that invalidates the credit count or expiry replaces the stored count, inventory and checked time while preserving the attempt ledger. A failed initial read on the next tick, and another failure after restart, cannot revive the superseded warning or first snapshot. Two-credit regressions inspect the disk from the next credit’s read callback for zero/unknown counts, changed expiry and a missing credit ID; interrupted-worker restart retains the same snapshot. Notification callbacks verify persistence before both fresh missing-credit cleanup and initial-read removed-credit cleanup. The project manifest explicitly records usage-independent eligibility, and metadata tests prevent the obsolete percentage threshold from returning and keep the release version consistent across the bundle, application constant, manifest, README and changelog.

Version 1.1.4 removes the application's usage threshold. Mock cases cover 0%, 8%, 30% and 100% remaining; either window low; missing or another bucket's usage windows; 1201/1200/1199/1/0 seconds until expiry; failed initial/fresh reads; expiry changes; unavailable/unknown counts; no-op server results; and same-key recovery even after usage is replenished. These are synthetic checks, not proof that the live service will accept a reset at every usage level. The existing 1.1.3 menu structure is retained. The local v1.1.4 update also succeeded: the installed universal binary matched the tested build, menu and worker each ran once, automatic-use and reminder settings plus attempt/reminder records were preserved, and the previous 1.1.3 bundle remained backed up. The native status reader showed the time-based policy and no old usage threshold. No real credit was consumed for testing, and no pixel/click verification was performed. Publication is separate from this local verification.

The unified installer adds isolated lifecycle tests using a temporary synthetic user directory and an injected OS/launchd adapter. They exercise fresh and repeated installation, retained off/on settings and pending keys, legacy handoff with a final post-stop ledger, build/start/write/health failures, interrupted replacement and forward-only activation recovery, concurrent installer/worker exclusion, removal and reinstall, and preservation of unrelated services. Regression cases also cover existing open-based menu login registration, exact loaded launchctl arguments, backup-directory symlinks and unsupported Program-only watcher definitions. No test changes the real home, login jobs, installed app or account. The installer's startup verification runs with inactive ownership; real activation and macOS login behavior remain live operational checks, not claims established by these doubles.

A local native installation and a repeat update were applied with this installer. Both login services ran as one menu and one worker, existing setting and recovery-record hashes stayed unchanged, and the installed app exported its actual menu with usage, details and enabled toggles. The app binary remained the existing 1.1.3 build; this change updates its installation lifecycle. The first attempt stopped before bundle replacement and was restored without record changes. A bounded service-removal wait was added; subsequent installation and repeat update succeeded. The original transient failure was not conclusively identified. No live reset-credit consumption, new accessibility authorization, reboot or pixel/click test was performed.

The reset runtime has 50 reset-status/time-zone checks and 174 engine checks, plus guarded mock stdio read and consume contract tests. All fixtures use fictitious data. The packaging check verifies an invalid-architecture build preserves the last good app. 39 compact-menu checks cover normal/unknown/stale counts, Seoul expiry, imminent expiry, unconfirmed outcomes, worker/notification failure and concise login/CLI warnings. The portable migration tests use temporary paths and synthetic keys, never launchd or the real CLI.

Coverage includes standby, exact 20-minute boundaries, usage-independent attempts, changed credits, missing/stale credit data, noCredit/nothingToReset/alreadyRedeemed, persisted intent failures, restart with the same key, exclusive process lease, reminders and denied notification permission. Asia/Seoul display is checked across a UTC date boundary.

Version 1.1.2 adds multi-credit pending recovery: retry delays and restarts cannot consume another credit, a fresh read with absent/changed credits cannot discard an unknown intent, and multiple pending intents each retain their stored key. A fake server simulates an actual reset followed by response timeout and confirms the original result on same-key replay without performing another reset. A separate test process verifies that the held worker lease excludes another process. Fresh inventory alone is not treated as successful redemption.

Version 1.1.3 verifies that missing, expired or changed pending credits still hold all consumption while another available credit receives its due reminder, both with auto-use enabled and disabled. The same-cycle fresh-read disappearance path uses the fresh available inventory for reminders. Reminder deduplication survives restart; turning reminders off does not authorize consumption or send an alert.

A local v1.1.0 deployment followed by the v1.1.1 menu update verified the installed version, a single native worker with no legacy consumer, actual menu construction, current settings and macOS notification authorization. Personal usage values and logs are not published here. No real credit was consumed for verification.

Actual expiry-banner display, real conditional redemption, reboot/wake behavior and a live rollback are separate operational checks and have not been demonstrated by the synthetic tests. The older standalone Python handoff has not been applied in this live native-to-native installation check. The 1.1.1 source changes menu presentation and version metadata. Consume eligibility, notifier and registered worker execution logic remain unchanged from 1.1.0; the local update verified one worker/menu, unchanged service plist/settings and the actual NSMenu tree. Normal first-screen rows decreased from 17 to 7 in the observed one-window case. Pixel capture and interaction clicks were not verified.

The repository scan covers tracked working files and every reachable historical blob, commit/tag metadata, and historical filenames for credentials, personal absolute paths, runtime state/binaries and private endpoints. It is a scoped pattern review, not proof that every possible secret representation is impossible. Synthetic fixture IDs and recovery keys are intentionally fictitious.
